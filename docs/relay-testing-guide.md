# Testing the VPS Slack Relay

The relay lets Slack/Discord messages reach a Claude Code session **without a laptop running** — a dedicated process on the VPS handles inbound and replies.

Architecture: grip-channel daemon (VPS, pm2, watches Slack/Discord) detects an allowlisted inbound message → POSTs an envelope to `relay-dispatcher` (VPS, pm2, `127.0.0.1:8787/event`) → dispatcher spawns one short-lived `claude -p` (CCH OAuth, no API key) → reply posted back via the channel. Per-channel conversation continuity: `state/relay/sessions/<channel>.txt`. Activity log: `logs/relay-dispatcher.jsonl`.

## 1. Health check (10s, any machine, no login)

```
curl -s https://your-gateway.example.com/health
```

Good = `"slack":{"connected":true}` and `"discord":{"connected":true}`. `whatsapp:false` is expected — the Hetzner IP is blocked by WhatsApp; not a relay fault.

## 2. Process check (20s)

```
ssh root@100.64.0.10 'sudo -u grip pm2 list | grep -E "relay-dispatcher|grip-channel"'
```

Good = both `online`. A `relay-dispatcher` restart count near 0 means it is stable (the old always-on listener crash-looped ~70x in 12 minutes; the dispatcher does not).

## 3. End-to-end test (proves laptop-independence)

1. Close or ignore every Claude Code session on your laptop.
2. In Slack `#nexus-chats`, post a message addressed to GRIP, e.g. `@GRIP relay test — reply OK and the current time`.
3. A reply should arrive in ~15-80 seconds, generated by the VPS.
4. Confirm it was the VPS, not a laptop:

```
ssh root@100.64.0.10 'tail -n 1 ~/.claude/logs/relay-dispatcher.jsonl'
```

Good = a fresh line with your message's timestamp, `claude_exit_code:0`, and your Slack sender id.

## Reading the activity log

Each line = one inbound message handled. `claude_exit_code:0` = success. `resumed:true` = the conversation thread was continued. `elapsed_ms` = round-trip time (cold ~40-80s, warm ~15s).

## Rollback (instant, reversible)

Remove the `GRIP_RELAY_WEBHOOK_URL` line from `~/.claude/.grip-channel.env` on the VPS, then `pm2 restart grip-channel`. Behaviour returns to the pre-relay state, byte-for-byte. Setting the variable again re-enables the relay.
